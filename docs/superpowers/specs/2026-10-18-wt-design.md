# wt: design spec

- **Date:** 2026-10-18
- **Status:** approved design, not implemented
- **Working name:** `wt`. The earlier name "Watertight" collides with an active npm package in the same category
  (github.com/camosss/watertight, "ungrounded claims fail the build"), so the final name is chosen in a separate brand task.
- **Source thesis:** `stateproof-watertight-complete-2026-10-18.md` (Watertight / StateProof). This spec keeps its property-first model,
  outcome semantics, and safety rules, and changes how properties are written, validated, and executed.
- **Family:** fourth project after Evergreen, Seaworthy, and Slipway. Same roadmap format (lanes, sizes, roadmap keys).

## 1. Problem

Unit tests, type checks, and green CI do not show that a change keeps state consistent across a database, a cache, and a broker.
A coding agent that refactors an update handler can leave a stale value in Redis, double-apply a redelivered event, or reintroduce a
stale-repopulation race, and nothing in the usual pipeline notices. Models getting smarter does not remove this: the bug lives in the
interaction between processes at runtime, and only executing it under the right conditions shows it.

## 2. Goal and success criteria

**North star.** When a coding agent changes code that touches a database, cache, or broker, running `wt` before pushing is as normal as
running the tests, and StateBench is how agents are measured on state correctness.

**Honest scope of the north star.** "Every agent on every push" is not realistic for a tool about state, because most repositories have no
stateful backend. The reachable version is: `wt scan` runs on every push in any repository with zero setup and stays silent when there is
nothing to say, and `wt verify` runs in CI for every repository with a stateful backend.

**Success criteria (gates, not forecasts):**

| Gate | Evidence | When |
|---|---|---|
| G1 Detection | 12/12 seeded bugs in `wt-bench` fail, 0 of 12 controls fail, every `fail` has a working replay | end of Phase 1 |
| G2 Agent value | Arm C (agent + wt) beats arm B (agent + Toxiproxy + Testcontainers) on pre-registered metrics, same model and budget | end of Phase 1 |
| G3 Real bugs | at least one accepted upstream issue or PR from a bug `wt` found in an open-source project | Phase 2 |
| G4 Retention | three outside teams keep `wt verify` in CI for 30+ days | Phase 6 |
| G5 Standard | one independent tool implements a `wt` spec format and passes the conformance suite | Phase 12 |

Gates do not block building. They decide what is promoted, marked stable, and announced. If G2 fails, the project pivots to shipping the
protocol proxies as a library (see section 10).

## 3. Decisions made in brainstorming

1. **Two layers.** A fast static layer (`scan`) for every push and an execution layer (`verify`) for CI.
2. **Zero-config scan.** `scan` works in a repository with no `wt` config and reports coverage facts, never a failure.
3. **Go first.** The tool is a single Go binary; the first analyzer targets Go services.
4. **Native analyzer (approach A).** `go/packages` plus `go/types`, not tree-sitter, so `rdb.Set` on a go-redis client is distinguishable
   from any other `Set`. Low noise is a requirement for a tool that runs on every push. Analyzers for other languages are native to those
   languages and emit the same `state-touch` format.
5. **Agents write properties; `wt` judges them.** The oracle-cost risk in the thesis moves to agents, which are good at drafting specs.
   Verdicts come only from execution.
6. **Protocol proxies are the moat.** `wt` sits between the app and Redis, NATS, and later Postgres, Kafka, and others, and injects
   command-aware faults: drop `DEL`, hold a `SET` until a signal, redeliver a message, cut a connection after statement N. This makes
   `verify` language-independent and makes races reproducible without instrumenting the app. Envoy's Redis filter only injects delay and
   error, and its delays block every later command, so it cannot build a stale-repopulation schedule.
7. **Mutation-validated properties.** A property becomes `active` only after `wt` shows it passes on the current code and fails under its
   matching fault. Mutation proves a property is not vacuous, not that it is correct, so a human promotes it in review (CODEOWNERS on
   `wt.yaml`).
8. **The eight modules from the thesis are packs, not engines.** Each is a property type plus proxy faults plus analyzer detectors.
9. **`wt init` edits `AGENTS.md` by default**, shows the diff, and accepts `--no-agents-md`.
10. **Roadmap scope:** 12 months with parallel agents. StateBench starts in Phase 1.

## 4. Architecture

```
                    CLI  ·  MCP  ·  Agent Skill  ·  GitHub Action
                                      │
        ┌─────────────────────────────┼─────────────────────────────┐
        ▼                             ▼                             ▼
   wt scan  (fast layer)        wt check-property            wt verify  (CI layer)
   ≤2s · no Docker · exit 0     mutation-validates a         Docker · isolated ·
                                new or changed property      pass/fail/unknown
        │                             │                             │
   analyzer ──► state-touch.json      └──────────┬──────────────────┘
   (per language)                                ▼
                                       Protocol proxies
                                       RESP · NATS · later PG wire, Kafka, AMQP, HTTP
                                       drop · delay · hold · reorder · redeliver · cut
                                                  │
                                       App under test + real Redis/PG/NATS
                                                  │
                                       Evidence: trace, seed, versions, replay
```

### Components

| Component | Does | Does not |
|---|---|---|
| `analyzer/<lang>` | Finds state touches: SQL writes, cache commands, publish and consume calls, with symbol, file, line, and target (key pattern, table, subject) when static | Judge anything; run code |
| `scan` | Joins state touches with the diff and `wt.yaml` `covers`; reports `COVERED`, `GAP`, `STALE` | Fail a push (exit 0 unless `--strict`) |
| `proxy/<protocol>` | Speaks the protocol, passes traffic through, applies a fault plan | Know about properties |
| `verify` | Starts the Compose env, routes the app through proxies, runs properties, compares current vs mutated vs base | Touch any target outside the Compose network |
| `check-property` | Runs a property clean and under its default mutation; proposes `draft → active` | Promote a property itself |
| `report` | Stable JSON (`wt.report/v0`), SARIF, Markdown PR summary, `wt replay <run-id>` | Store seed data or secrets |

**Dependency rules.** The analyzer knows nothing about `verify`. Proxies know nothing about properties and can ship as a standalone
library. The core owns property semantics, outcomes, and evidence; adapters own protocol details. No `if backend == kafka` in the core.

### Proxy design rules

1. Implement the smallest slice of each protocol that faults need; pass every other command through byte for byte.
2. Fault plans are data (`drop`, `delay`, `hold-until`, `reorder`, `redeliver`, `cut-after`), matched by command and key or subject pattern.
3. A `hold-until` fault on one connection must not block other connections. This is what reproduces stale repopulation.
4. Every proxy records an ordered event log with monotonic timestamps; the log is the replay source.

## 5. Module packs

| Pack | Property types | Faults | Analyzer detectors | Phase |
|---|---|---|---|---|
| Cache | `read_after_write`, `bounded_staleness` | RESP drop `DEL`, hold `SET` | go-redis, rueidis | 1 |
| Event | `idempotent_effect`, `no_lost_event` | NATS redeliver, drop ack, drop publish | nats.go | 1 |
| Concurrency | `concurrent_invariant`, stale repopulation | schedule plans across proxies | n/a | 2 |
| Replica | `bounded_staleness` | PG wire delay on replica connection | replica DSN detection | 2 |
| Transaction | `atomic_under_interruption` | PG wire cut after statement N | transaction boundaries | 2 |
| Projection | `convergence` | HTTP proxy for Elasticsearch, OpenSearch, Meilisearch | search clients | 3 |
| Workflow | `idempotent_step`, business invariant | container restart mid-workflow | Temporal, BullMQ, Celery | 3 |
| Recovery | `recovers_within` | container kill, network partition | n/a | 4 |
| Later | outbox integrity, tenant isolation, migration invariants, projection monotonicity | reuse | reuse | 4+ |

## 6. Property format (`wt.yaml`)

```yaml
version: 0
env:
  compose: compose.test.yaml
  app: api
  seed: make seed

properties:
  - id: user-name-read-after-write
    type: read_after_write
    covers: [internal/user.UpdateUser, internal/user.GetUser]
    write: {http: "PATCH /users/42", body: {name: "$fresh"}}
    read:  {http: "GET /users/42", observe: "$.name"}
    expect: equals_written
    within_ms: 500
    status: active

  - id: order-created-once
    type: idempotent_effect
    covers: [internal/inventory.OnOrderCreated]
    deliver: {nats: orders.created, payload: fixtures/order-19.json, times: 2}
    observe: {sql: "SELECT stock FROM products WHERE id = 7"}
    expect: same_as_single_delivery
    status: draft
```

- `$fresh` is a unique value generated per run, so agents never guess values and runs do not collide.
- `covers` links the two layers; `scan` checks that each symbol exists.
- Each property type has a default mutation, so agents never write one.
- Observations use SQL, JSONPath, and HTTP only. No new DSL.
- Lifecycle: `draft` → (`check-property` passes clean, fails mutated) → human sets `active` in a reviewed PR → `deprecated`.

## 7. Outcomes and report

| Status | Meaning | Exit code of `verify` |
|---|---|---|
| `pass` | Only the executed scenarios passed; always carries `scope` and `runs` | 0 |
| `fail` | Witnessed violation with replay; `"reproducible": "k/n"` when not deterministic | 1 |
| `unknown` | Ran but evidence insufficient (timeout, app did not start, `non_isolated_target`); never counted as pass | 2 |
| `not_tested` | Relevant but not run | 2 under `--affected`, else 0 |

Report outputs: JSON (`schema: wt.report/v0`), SARIF, Markdown PR summary. Every `fail` has `wt replay <run-id>`.

## 8. Agent workflow and distribution

```
agent edits code
  → wt scan --diff HEAD
     ├─ COVERED → done; CI runs verify --affected
     └─ GAP → agent drafts property from Skill template
            → wt check-property <id>
            → property lands as draft in the same PR → human promotes
CI: wt verify --affected → fail → agent reads JSON + replay → fixes → reruns
```

Channels, in order: Go binary (go install, Homebrew, install script) with npm and PyPI wrappers; Agent Skill; `AGENTS.md` line written by
`wt init`; GitHub Action with PR comment and SARIF; MCP server with three tools (`scan`, `check_property`, `explain`); optional pre-commit
hook that runs `scan` only.

## 9. Safety

- `scan` never executes code, uses no network, and needs no Docker.
- `verify` executes code; the Skill tells agents to ask before running it on an untrusted repository.
- Proxies connect only to services inside the Compose network. A target outside it makes the run `unknown` with `non_isolated_target`.
  There is no bypass flag.
- Bounded run time, redelivery count, CPU, and memory.
- Reports keep only observed values and `$fresh` values; no seed data or secrets in artifacts.
- No automatic telemetry.

## 10. Evidence program

- **`wt-bench` → StateBench.** A public Go shop service (HTTP, Postgres, Redis, NATS) with 12 seeded bugs in six classes (missing
  invalidation, wrong-key invalidation, stale repopulation, duplicate consumption, ack before commit, wrong TTL) and 12 controls (6 correct,
  6 permitted-eventual). Each bug is a git tag. Grows into StateBench: hundreds of cases across languages, a held-out split, and a leaderboard.
- **Agent A/B/C.** A: agent + tests + Testcontainers. B: agent + Toxiproxy + Testcontainers. C: agent + `wt`. Same model and budget;
  metrics pre-registered in the repo; results published whatever they show.
- **Ecosystem scans.** `wt scan` over 50 open-source Go services using Redis or NATS, published as a "state of" report; properties for
  five of them; any real bug goes upstream first.
- **Pivot if G2 fails.** Ship the proxies as a Go library and Testcontainers module for deterministic fault and race testing.

## 11. Business goals

| Goal | Mechanism |
|---|---|
| Show value | 30-second recording: agent edits, `wt` finds a race with a deterministic replay, agent fixes it; StateBench results page |
| Visitors | "State of cache invalidation in Go" (and later TS, Python) reports; one post per real bug, titled by the search people make |
| Real feedback | `wt feedback` opens a prefilled issue from a redacted report; every `unknown` links to "report this"; no telemetry |
| Install rate | zero-config `scan`, `wt init` adds AGENTS.md line, Skill, and Action in one command; first useful output in under 60 seconds |
| Targeted users | Go teams with stateful services; Gophers Slack, r/golang, Golang Weekly; testing examples contributed to go-redis and nats.go docs |

## 12. Non-goals

Proving general correctness; inferring business invariants from names; replacing Jepsen, Antithesis, outbox infrastructure, or chaos
platforms; running against production; autonomous code rewrites; a new general-purpose DSL.

## 13. Risks

| Risk | Mitigation |
|---|---|
| Agent-written properties confirm their own bug | mutation validation, base-commit comparison, human promotion |
| Maintenance cost of many proxies and analyzers | minimal protocol slices, conformance suite, no merge without a `wt-bench` fixture, outside maintainers per ecosystem |
| Scan noise kills adoption | type-resolved detection only; `GAP` only for diff-touched symbols; never fails a push by default |
| Flaky verify | per-property `runs`, reproducibility fraction in reports, proxies record ordered logs |
| Name collision | separate brand task before public launch |
| G2 fails | pivot to proxy library (section 10) |
